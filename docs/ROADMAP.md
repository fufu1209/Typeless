## 未完成，以及为什么

### 1. 池内逐号额度（不切换就读完 50 个号）

**现状**：直读只能读**当前登录账号**；`scripts/audit-account-pool.js` 走 Node 直连，
命中 JA3 墙（HTTP 418），拿不到真实数字。

**为什么不在这一版**：两条可行路线都有必须先解决的前置条件：

- **路线 A：每号一个浏览器 profile，跑 web 客户端**
  - 可行依据：web 客户端同样带签名，且 Chromium 的 JA3 在白名单内；
    `Automation/BrowserProfiles/` 里已经有注册时留下的账号 profile。
  - 前置条件：需要验证「profile 里的 typeless.com 会话是否仍然有效」、
    「50 个 profile 串行启动要多久」（实测单次冷启动 2–4 秒，全量 2–3 分钟）、
    以及「并发/频繁登录会不会触发风控」。这些都要在真机上先量，不能拍脑袋写。
- **路线 B：在 App 内切换会话再读**
  - 需要 `auth:login` / `store:use` 的写入语义（目前只验证了 `auth:get-current` 读）；
  - 且切换会改变**用户正在用的账号**，必须做到「读完立刻切回」，
    失败时可能把用户登出 —— 风险高于收益，暂不做。

**下一里程碑的验收标准**：给 10 个账号跑一遍，`used/limit` 全部为服务端原值、
总耗时 < 60 秒、不改变当前登录账号、无额外验证码。

### 2. 邮箱服务商抽象（不再绑死 MoeMail）

**现状**：创建邮箱、读邮件、取验证码都直接调 MoeMail HTTP。

**为什么不在这一版**：这不是「加个 if」——需要先定义协议（创建地址 / 列邮件 /
取正文 / 删除地址 / 错误语义），再把现有 3 个调用点（`+MoeMail`、`+MoeMailHTTP`、
注册轮询）迁过去，UI 还要增加「服务商选择 + 凭据」。半成品抽象比现在的直连更危险。

**下一里程碑的验收标准**：至少两个实现（MoeMail + 一个 IMAP/临时邮箱），
用同一份 `EmailProvider` 协议跑通「建号 → 收码 → 取码」，且切换服务商不用改注册链路。

优先级低于上面两项，等池内体检落地后一起做。
